# Friction log

Every snag I hit while building Dock Radar in one day, on both sides:
**consumer** (integrating an external data source into Supabase) and
**publisher** (making it installable by others, listing it).
I also logged what worked well, because that's worth protecting too.

Severity: 1 = minor annoyance, 2 = cost real time or needed a workaround, 3 = blocker. ✓ = went well.

## Consumer side: top 3 frictions

1. **Wiring pg_cron to an Edge Function is manual and fails silently (#3).** It's the core pattern for any "poll an external source" integration. Today it needs the URL and key copied into Vault by hand, and gives no signal when they're missing. A built-in way to call your own function from SQL would remove the whole problem.
2. **The scheduling example uses a public key (#9).** The quickest path produces an endpoint anyone can call. The secure version is only a small change, but you have to know to look for it.
3. **Local testing is heavy (#1, #2).** Before writing any code, you need a global CLI install that npm doesn't support and a Docker stack of several GB. Both have workarounds, but they're the first thing a new integrator meets.

What went well: the CLI templates are current (new API keys, `@supabase/server`). Auth errors explain themselves (#10). Checking production from the terminal is quick (#11). From an empty folder to production data every 5 minutes took under an hour, with Claude Code as a pair.

## Publisher side: top 3 frictions

1. **The catalog has no place for community integrations (#4, #5).** The criteria (a registered business, revenue or VC backing, legal documents, SLAs) make sense for partners Supabase vouches for. But they leave out the individual developers a "developers build integrations" marketplace depends on. Community projects do have homes: the community-run [Made with Supabase](https://www.madewithsupabase.com) showcase and the Community Content Program. Both sit outside the official Marketplace, though, so they don't help users *find and install* integrations.
2. **Installing takes too much trust (#7).** An installer needs arbitrary SQL and read access to every API key. That's hard to justify to users for a small integration.
3. **There's no unit of distribution (#8).** An integration is migrations, functions, secrets and schedules together, but nothing packages them. Every publisher writes their own install README, and every installer follows it by hand.

On the positive side, registering an OAuth app takes a couple of minutes (#6). The hard part is everything around it: packaging, scopes, and somewhere to be listed.
